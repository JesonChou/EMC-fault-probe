# 1.项目任务

根据中文资料构建电磁兼容故障库，利用LLM对各种EMC故障资料进行语义分割，转化为JSON格式输出，核心是利用 LLM 的**信息提取、知识整合、语义理解与生成能力**，将分散、非结构化的故障数据转化为结构化、可复用的故障知识体系。

需要完成的几项内容为：

|             内容              |                           说明                            |
| :---------------------------: | :-------------------------------------------------------: |
|     结构化的EMC故障数据库     |      包含至少几十到上百条故障条目，每条都有完整字段       |
|      可查询的故障库系统       | 可以是 Web 页面、小程序或命令行工具，支持中文自然语言查询 |
|           项目报告            |  说明数据来源、处理流程、LLM 使用方式、故障库结构设计等   |
| 展示LLM在故障数据提取中的作用 |     展示 Prompt 示例、抽取前后的对比、语义去重效果等      |

# 2.项目基础任务思路

根据项目任务的描述，我们完成该项目的思路如下，主要分为5个步骤，分别是”历史数据收集“、”数据预处理“、”LLM提取结构化信息“、”构建数据库”以及“故障库应用设计”。

## 2.1 历史故障数据的收集

这一部分需要使用各种中文语料库，如万方数据、知网、各种网页以及大语言模型如Deepseek和ChatGPT，从上述信息源中获取EMC故障原始数据。例如，我们在万方数据库中查询到一篇题为《空间光学有效载荷电磁兼容故障诊断》的文献[^1]，其中一段包含了载荷干扰源（即==故障原因==）的描述：

> 载荷的干扰源可分为载荷内设备产生的干扰源和载荷外部干扰源。载荷内部产生的干扰主要包括以下几方面：
>
> 1）开关电源和变换器引发的干扰。
>
> 2）脉冲数字电路引发的干扰。
>
> 3）继电器及触点等引发的干扰。
>
> 4）步进电机引发的干扰。
>
> 5）设备线缆间的相互耦合干扰。

我们可以利用LLM对这些文字信息进行处理，将其转化为JSON等结构化数据格式，用于构建EMC故障库。

## 2.2 数据预处理

我们需要对从不同途径收集来的故障信息进行清洗。主要的工作如下：

1. 去除无关符号、空白、重复内容；
2. 将不同格式（PDF、Word、网页）的资料转为统一格式（如 TXT 或 JSON）；
3. 利用LLM合并“同义不同述”的故障记录。

> [!NOTE]
>
> 问题1：如何将PDF、Word、HTML等格式的资料转化为JSON格式？
>
> 方案1：使用ConvertTool等在线工具转换。需要试一次，看下转换结果。

## 2.3 利用LLM提取结构化信息

这一步需要设计合适的Prompt，让LLM从非结构化的故障描述中提取结构化字段，例如：

|  字段头  |          字段内容          |
| :------: | :------------------------: |
| 故障对象 |   如“电机A”、“通信模块”    |
| 故障现象 |  如“通信中断”、“辐射超标”  |
| 故障原因 | 如“接地不良”、“滤波器失效” |
| 解决方案 | 如“重新接地”、“更换滤波器” |
| 故障等级 |      如“严重”、“一般”      |
| 发生频率 |      如“高频”、“偶发”      |

一个基础故障信息提取Prompt示例如下：

> [!IMPORTANT]
>
> 你是一个电磁兼容故障分析专家，请从以下中文文本中提取电磁兼容相关的故障信息，按照JSON格式返回：
>
> **提取字段要求：**
>
> - 故障对象：发生故障的具体设备、部件或系统
> - 故障现象：可观察到的电磁兼容异常表现
> - 故障原因：导致故障的根本原因分析
> - 解决方案：修复故障的具体措施或方法
> - 故障等级：根据影响程度判断（致命/严重/一般/轻微）
> - 发生频率：高频/中频/低频/偶发（根据文本描述推断）
>
> 
>
> **待分析文本：**{input_text}
>
> 
>
> **输出要求：**
>
> - 只输出JSON格式，不包含其他说明文字
> - 如果某个字段无法确定，设为空字符串
> - 保持术语的专业性和准确性

> [!CAUTION]
>
> 上述方案需要尝试，根据输出效果对Prompt进行调整。

## 2.4 构建故障库

利用2.3中所讲述的思路提取出结构化信息后，利用这些信息来构建故障库，主要涉及故障库的存储形式以及数据结构的设计：

1. 将提取的结构化数据存入数据库（如 MySQL 或 MongoDB）；
2. 建立“故障-原因-解决方案”之间的关联关系，并使用故障码来表示不同类型的故障。

## 2.5 故障库的应用功能设计

上述的数据处理及故障库构建主要采用的是第一个技术路径，即：

> **一、基于 “历史故障数据” 的自动化提取与结构化（最核心、最常用）**
>
> 该方法适用于已有大量历史故障记录（如设备维修日志、客服工单、故障报告）的场景，核心是通过 LLM 将非结构化文本（如自由描述的故障现象、维修记录）转化为 “故障 - 原因 - 解决方案” 的结构化三元组，是故障库的基础构建方式。

围绕这一路径的应用设计（即实现用户使用中文查询故障即解决方案），我们的思路如下：

1. 将前述步骤所建立的数据库存储为某种格式的数据文件，如MySQL、JSON格式等；
2. 使用Python[^2]编写脚本，测试不同的用户输入（例如用户输入”辐射发射超标“）能否准确地匹配到故障库中相应的故障词条，并返回故障码和解决方案；
3. 步骤2测试完成，准确度达到要求后，使用PyQt5设计用户交互界面[^3][^4]；
4. 可以尝试在程序中嵌入LLM[^5]，利用LLM进行模糊或近义语义匹配，优化用户体验。
